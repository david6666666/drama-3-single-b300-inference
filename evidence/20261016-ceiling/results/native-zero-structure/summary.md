# 固定45个FP8矩阵的零结构审计

结论：样本中较大的零结构集中在L0，且是gate/up完整行与down对应完整列的**同一组hidden channel**，不是均匀散布零。L1仅少数channel，L2/L19/L39没有完整零channel。不能从这些checkpoint字节判断形成原因，也不支持裁剪channel、跳过专家、2:4 sparse MMA或改动原top8计算。

本次仅CPU读取指定L0/L1/L2/L19/L39、expert0/127/255的gate/up/down，共45个矩阵、45MiB。每个矩阵原始bytes保存到 `raw/*.bin`，`result.json`记录原checkpoint文件、数据偏移、shape、dtype、header/raw SHA256；与旧审计重叠的27个矩阵hash完全一致。未初始化GPU，未改checkpoint/runtime/权重/scale。

## 正负零和空间结构

E4M3原字节0x00与0x80分别是正零、负零。旧 `zero_byte_fraction`只统计0x00；例如L0 e0 gate正零27.2869% + 负零27.4013%，总数值零54.6882%。e0/127/255三投影的完整零channel比例分别54.6875%、14.0625%、59.375%，每矩阵仅另有2…14个零散零。全部45矩阵排除完整零channel后，每个1MiB矩阵剩余数值零仅2…25个。

每个专家gate/up的完整零行索引与down的完整零列索引逐项相同；原索引和连续run均保存在JSON。L0这些channel分散于0…511，不是一个连续尾部；L1例如e0只有327、433。零channel内部正负号约各半，L0边际sign entropy约0.999997…1bit/byte。这个边际统计不证明sign之间独立，但说明**把所有零替换0x00不符合原byte精确要求**。不能仅根据有大量零就宣称是随机下溢或训练剪枝；缺少量化前权重与生成过程证据。

沿行主序K方向的128-byte块：L0 gate/up e0/127/255分别4480/1152/4864个全数值零块（总8192）；这些块仍含混合正负零，没有全0x00或全0x80的128-byte块。down的全数值零128-byte块均为0，因为其零以列分布。45矩阵中，所有对齐128×128 tile均非全零。

这也不是可直接使用的2:4结构：沿真实K方向每4个元素，gate/up零channel行内是4个全零，其他行几乎4个全非零，exactly-two-zero比例为0。L0 down恰好2零比例为36.7191% / 6.2523% / 31.2504%，但各矩阵仍有大量0或1零group。**45/45矩阵均不满足所有K-group至多2个非零**。这里没有尝试重排weight、合并零符号或改MMA。

## 可以无损表示，但便宜执行尚无证据

CPU演示格式仅用于计算字节预算：每矩阵64B channel bitmap；非零channel原字节原序保留；完整零channel只存每个原字节的1bit sign，解码为0x00/0x80。45/45逐byte往返精确，原shape和索引全部恢复；未实现GPUdecoder、未触及scale。采用无收益时原格式fallback即可避免64B膨胀。

L0三专家每个原gate+up+down合计3MiB，此格式分别为1,640,640 / 2,758,848 / 1,511,616B，节省47.8455% / 12.2986% / 51.9470%。这是L0局部存储机会；L1只有约10…16KiB/专家，另三个样本层无此预算。纯初始化时解压后继续原dense weight，只改变存储/准备时间，不降低每步MMA读量。

若每步先解压到全局dense buffer再调用原native kernel，必须额外写入完整3MiB且native再读完整3MiB，还要读取压缩payload；逻辑流量可能比原3MiB读取更大。缓存命中、L2写回和复用会影响实际DRAM量，不能直接从这些逻辑字节推导时间，但它足以否定“省文件字节自动等于省runtime带宽”。

真正可能避免这个额外dense写入的路径是：在原weight staging阶段把压缩payload**还原成完全一致的FP8字节**送入相同shared布局，然后维持原scale、K128分组、MMA顺序和finalizer。它需要改变TMA/loader接口，并增加bitmap、sign unpack与同步，已超出低成本包装；此前Prims/native供数差异及完整MoE负结果提示不能假定受益。这个CPU审计不授权新的GPUdecoder或替换原生计算。

因此当前最小低风险路线仍是已在单独micro gate证明actualflag1、逐byte和lifetime的硬件generic compression，由完整native MoE相同调用确认是否有实际收益。若该路线无收益，现有样本只支持“L0有显著无损存储结构”，**没有发现已可兑现、覆盖全模型的大预算低成本替代**。不据此扩大盲扫或宣称能够达到6765。
