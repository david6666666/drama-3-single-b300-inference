# Independent BF16 Lt capability review

The original strict run selected zero candidates. Its 0.024148 ms difference is an A/A observation, not algorithm performance. No original capability gate or result should be reclassified.

The two exact serialized algo66 configurations have actual BF16 layouts (enum14), FP32 compute (68), and FP32 scale (0). The eight full-output range/cancellation/accumulation diagnostics match rounded FP64 byte for byte. The corrected independent C++ probe returns flags0x10202 for both configurations using the same cuBLAS13.1.1 library as Python. The initial C++ run loading system13.7 is retained and excluded from this same-library claim. This excludes a Python-only capability-binding error and ordinary unscaled FP16 input narrowing on the tested values. It does not establish every input or every internal instruction.

Official cuBLAS documentation distinguishes INPUT_16F (inner multiply-accumulate input is half) from INPUT_16BF (bfloat16), and ACCUMULATOR_32F identifies the inner FP32 accumulator. Thus 0x10202 cannot simply be renamed a generic 16-bit flag. No confirmed vendor explanation for this observation was found. [NVIDIA cuBLAS numerical flags](https://docs.nvidia.com/cuda/cublas/index.html#cublaslt-numerical-impl-flags-t)

A shared hardware instruction family is a possible explanation, not an established diagnosis: NVIDIA's MmaF16BF16Op uses the same kind::f16 family for supported FP16 and BF16 operations. A kernel name or kind::f16 alone therefore cannot establish the actual operand format. [NVIDIA CUTLASS MmaF16BF16Op](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/cute_dsl_api/cute_nvgpu_tcgen05.html#cutlass.cute.nvgpu.tcgen05.MmaF16BF16Op)

I recommend a separate, explicitly unresolved-datatype artifact gate, bound to the two complete algorithm byte strings, exact shapes/strides/descriptors, GPU, and shared-library hashes. It can test the real captured inputs without changing the original filter or production code. Every eager and CUDA-graph replay output must pass full byte equality to the established F.linear reference, with inputs, weights, guards, and RNG unchanged. A failed exact gate stops that candidate; numerical tolerance must not replace the gate. Retain graph capture allocations through replay, compare the captured output buffers, and retain the recorded BF16 reduction/backend policy in the control.

The existing diagnostic uses one exponent magnitude per entire operand tensor. A useful bounded extension is a dot product containing interleaved reciprocal powers (+80/-80) in both operands, with exactly representable products and sum. This can exclude additional conversion hypotheses but still cannot prove the entire BF16 domain. Synthetic inputs and finite real samples do not resolve the official capability contradiction by themselves.

Actual kernel identity can be recorded alongside this gate. A complete projection-sequence improvement below the declared 0.3 ms threshold should stop this direction before costly disassembly. Before any runtime promotion or claim of an established native BF16 implementation, obtain the actual MMA operand-format/descriptor evidence (including the path from input storage to the MMA operands) or a clear NVIDIA explanation. Do not infer datatype from opaque serialized algorithm internals. The bounded gate is investigative evidence, not a general capability whitelist.
